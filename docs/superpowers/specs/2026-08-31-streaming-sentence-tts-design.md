# LumiLamp 方舟流式短句 TTS 设计

日期：2026-08-31

## 目标与范围

将当前“ASR 完成 → 方舟完整回答 → TTS 完整音频 → 播放”的串行回答路径改为：方舟 SSE 流式输出文本，按自然短句切分，并由单一 TTS/播放消费者按原始顺序播报。目标是显著缩短从用户说完问题到首次出声的时间，同时继续保持现有半双工安全边界。

本阶段只修改树莓派语音软件。不得访问 GPIO、ESP32-S3、串口、舵机或固件；不实现播报中打断、全双工、回声消除或 TTS 音频 WebSocket 流。

## 已确认的产品决策

- 优先保证自然的完整短句，不采用几个词就播报的极低延迟方式。
- 中文句号、问号、感叹号、分号是优先句界；逗号只在长句超限时作为退化句界。
- 方舟流在已有句子播放后中断时，保留已经播出的内容，播放本地固定提示“网络好像断开了”，并结束本轮，不发起整段重试。
- TTS 仍使用现有 HTTP 合成 WAV 接口；TTS 音频边生成边播放留给后续独立任务。
- 保持严格半双工：系统音频播放、方舟流和 TTS 合成期间不打开普通 ASR 或 KWS。

## 协议依据

现有方舟 `POST https://ark.cn-beijing.volces.com/api/v3/chat/completions` 请求继续使用 Bearer API Key、当前 `ARK_MODEL_ID`、有限会话历史和简短角色提示。新请求增加 `stream: true`。响应按 SSE `data:` 帧传输，`data: [DONE]` 表示正常结束；每个普通帧按 OpenAI 兼容 `choices[0].delta.content` 提取新增文本。可选 usage 末帧不包含文本，不应当作错误或句子。

当前 API 契约以火山方舟官方 ChatCompletions 文档为准：<https://api.volcengine.com/api-docs/view?action=ChatCompletions&serviceCode=ark&version=2024-01-01>。

## 架构与数据流

```text
USB 麦克风
  → 流式 ASR（得到最终问题）
  → ArkSentenceProducer（SSE 文本）
  → SentenceSegmenter（自然短句）
  → 有界 asyncio.Queue，最大 3 句
  → SentencePlaybackConsumer（TTS HTTP WAV → USB 扬声器）
```

`ArkSentenceProducer` 只负责请求、SSE 帧解析、完整回答累积与短句入队；不得调用 ALSA 或 TTS。`SentencePlaybackConsumer` 只从队列按顺序读取短句、合成唯一临时 WAV、播放并删除；不得访问方舟或会话历史。编排器负责创建两个任务、取消、错误归并、状态机边界及最终历史写入。

队列容量固定为 3。生产者在队列满时等待消费者，限制长回答的内存占用和云端文本提前积压；消费者只运行一个实例，保证音频永不重叠。

## 分句规则

`SentenceSegmenter` 维护未发送文本缓冲：

1. 每次收到非空 `delta.content` 都追加到缓冲。
2. 遇到第一个 `。！？；` 时，连同该标点输出前缀短句。
3. 未遇句末标点且缓冲达到 30 个汉字等价字符时，优先在最近的 `，、` 后切分；不存在逗号时在 30 字处硬切。
4. 收到 `[DONE]` 时，输出剩余非空文本作为最后一句。
5. 空白增量、usage 帧、SSE keepalive 与 `[DONE]` 均不得产生空句。

切分器是纯组件，直接以单元测试覆盖中文标点、多句单帧、跨帧句子、长句和结束残余文本。

## 会话与历史

收到 ASR 最终问题后进入 `THINKING`。一旦第一条完整短句准备播放，状态进入 `SPEAKING`，但普通 ASR 仍保持关闭，直到生产者、消费者都成功结束且最后一句播放完毕。

生产者在正常 `[DONE]` 后将所有实际生成文本拼成完整回答；消费者成功播放所有已入队句子后，才向 `ConversationHistory` 原子追加本轮“用户问题/完整回答”。异常、取消或只播放错误提示时不追加不完整回答。全部完成后继续复用现有约 300 ms 播放后保护时间和 30 秒连续对话窗口。

## 错误、取消与资源释放

- 方舟在任何短句产生前失败：取消消费者，播放本地错误提示，结束本轮。
- 方舟在至少一条短句已入队或已播放后失败：停止继续生产；消费者清空已排队正常短句后播放一次本地错误提示，结束本轮，不重试。
- 单句 TTS 合成或播放失败：取消生产者，丢弃后续队列，删除当前临时 WAV，结束本轮。
- `Ctrl+C`、会话取消或设备错误：取消并等待生产者与消费者；关闭方舟 HTTP 响应；删除所有本轮临时 WAV；保持已有 `arecord`/`aplay` 自有进程清理规则。
- 任何异常日志只含稳定阶段名、脱敏请求 ID（若存在）、已播放句数与时长，不含问题、回答、密钥、请求头、SSE 原始正文或音频。

本地错误提示在第一次实现前通过现有 TTS 显式准备流程生成并缓存；运行时不得静默创建或下载该提示。

## 延迟日志

保留现有 `voice_latency` 单行日志，并扩展为：

```text
voice_latency status=ok asr=… ark_first_sentence=… first_audio=… answer_complete=… total=…
```

`ark_first_sentence` 是从 ASR 完成到第一条可播放短句入队；`first_audio` 是从 ASR 完成到第一句实际播放结束前的首次音频开始时刻；`answer_complete` 是从 ASR 完成到最后一句播放结束。失败日志包含 `failure_stage` 和 `sentences_played`。不输出对话文本。

## 实施顺序

1. 为 Ark SSE 请求和严格帧解析添加纯协议测试与流式客户端。
2. 实现并测试纯 `SentenceSegmenter`。
3. 新建短句队列生产者/消费者协议，使用假的 Ark/TTS/播放器覆盖顺序、容量、取消与错误。
4. 改造 `VoiceLoop`，让现有非流式路径可被新流式适配器替换；保留原有 30 秒状态机和半双工测试。
5. 生成并验证本地“网络好像断开了”缓存提示 WAV，需在实际云端请求前再次确认。
6. 运行全套离线测试、编译和差异检查。
7. 在用户确认后进行最小方舟流式协议验证，再进行一次真实 USB 单轮延迟测量；比较 `first_audio` 与当前约 14–15 秒总延迟基线。

## 验收标准

- 方舟请求带 `stream: true`，能严格处理 SSE、`[DONE]`、空增量、usage 帧和协议错误。
- 短句保持原始顺序，TTS/ALSA 从不并发播放。
- 云端文本接收可与第一句之后的 TTS/播放并行。
- 首次出声基线目标为 3–6 秒；若真实模型/网络无法达成，日志能明确归因到 ASR、Ark 首句或 TTS/播放阶段。
- 中途断网不会重复已播内容，不泄露文本或凭证，且只播放一次本地错误提示。
- 完整成功回答才写入历史；失败、取消与中断回答不写入历史。
- 所有单元测试无网络、无麦克风、无扬声器；真实云端/USB 验证单独报告。
- 不执行固件上传、ESP32-S3 通信、舵机控制或装机机械验证。

## 验证边界

Static check：接口、句子规则、队列容量、缓存命名、密钥脱敏与配置检查。

Code test：纯 SSE/切分/队列/状态机/取消/清理模拟测试；不得访问网络或真实音频。

Physical-hardware validation：仅在用户确认后，分别报告方舟流式云端请求、TTS 合成、USB 扬声器播放、USB 麦克风闭环和目标树莓派整套语音路径。不得将这些结果表述为 ESP32、固件或舵机验证。
