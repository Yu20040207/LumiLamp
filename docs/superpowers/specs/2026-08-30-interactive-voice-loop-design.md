# LumiLamp 本地唤醒与豆包交互式语音闭环设计

日期：2026-08-30

## 目标与范围

在 Raspberry Pi 4B 上实现第一版半双工语音闭环：本地离线识别唤醒词，播放本地缓存的随机唤醒回应，随后使用已验证的豆包流式 ASR 2.0 获取文字，通过火山方舟文本模型生成回答，再用豆包语音合成模型 2.0 和 USB 扬声器播报。

本轮只涉及树莓派语音软件和 USB 音频设备。不得访问 GPIO、ESP32-S3、串口或舵机，不改变现有接线和供电配置。第一版不支持播报中打断；打断、回声消除和全双工对话留到后续独立设计。

## 已确认的交互行为

- 休眠时仅在树莓派本地监听 `露米` 和 `你好露米` 两个唤醒短语。
- 唤醒音频不上传云端，也不写入磁盘。
- 唤醒成功后随机播放以下四句之一，文字必须保持一致：
  - `我在呀`
  - `你好呀`
  - `嗯？`
  - `请吩咐`
- 四句固定回应由豆包 TTS 首次生成并缓存为本地 WAV；正常唤醒不重复请求云端 TTS。
- 播放唤醒回应期间暂停麦克风识别；播放结束约 300 ms 后开始收集用户问题。
- 用户问题经过豆包流式 ASR 2.0、火山方舟文本模型、豆包 TTS 2.0 后由 USB 扬声器播放。
- 每次回答播放完成后进入 30 秒连续对话窗口，窗口内无需重复唤醒；每次有效交流重新计时。
- 30 秒内没有新的有效语音则安静返回休眠。
- 连续两次云端或处理失败则安静返回休眠，防止无限重试。

## 架构

采用单进程、显式状态机和隔离适配器。会话编排器只管理状态转换和组件调用，不包含供应商协议、音频设备命令或模型实现。各组件均通过小接口连接，便于单元测试和后续替换。

```text
USB 麦克风
    │ 16 kHz / 16-bit / mono PCM
    ▼
本地 sherpa-onnx KWS ──未唤醒──> 继续休眠监听
    │ “露米”或“你好露米”
    ▼
随机选择并播放本地唤醒 WAV
    │ 播放结束 + 300 ms
    ▼
本地 VAD/分段 ──> 豆包流式 ASR 2.0 ──> 识别文字
                                              │
                                              ▼
                                      火山方舟文本模型
                                              │ 回答文本
                                              ▼
                                      豆包 TTS 2.0
                                              │ WAV/PCM
                                              ▼
                                         USB 扬声器
                                              │
                                      30 秒连续对话窗口
```

## 状态机与数据流

状态为 `SLEEPING`、`WAKING`、`LISTENING`、`RECOGNIZING`、`THINKING` 和 `SPEAKING`。

1. `SLEEPING`：持续向本地 KWS 提交内存 PCM。命中任一唤醒短语后进入 `WAKING`。
2. `WAKING`：随机选择并播放缓存回应。播放时不运行普通 ASR，结束约 300 ms 后进入 `LISTENING`。
3. `LISTENING`：本地 VAD 等待有效语音。保留短预滚缓冲，避免云端 ASR 丢失用户开头；检测到语音后才建立云端 ASR 会话。连续静音 800 ms 或单轮达到 10 秒时结束。
4. `RECOGNIZING`：接收豆包流式 ASR 的部分结果和最终结果；只有非空最终文本才进入 `THINKING`。
5. `THINKING`：把本轮用户文本和有限会话上下文发给方舟模型，得到简短中文回答。
6. `SPEAKING`：将回答交给豆包 TTS，完整播放后等待约 300 ms，再返回 `LISTENING` 并重置 30 秒计时。
7. `LISTENING` 达到 30 秒截止时间且没有有效语音时返回 `SLEEPING`。

第一版严格半双工：任何系统音频播放期间都不进行 KWS 或普通 ASR。后续打断功能不得通过简单地同时打开录放实现，必须另行评估声学回声消除、回声参考信号和误唤醒策略。

## 组件职责

### AudioDeviceResolver

- 麦克风按 USB ID `08bb:2902` 查找，优先返回稳定 ALSA 名称 `plughw:CARD=Device,DEV=0`，不写死数字声卡号。
- 扬声器按 USB ID `1b3f:2008` 查找，优先返回稳定 ALSA 名称 `plughw:CARD=Device_1,DEV=0`。
- 设备不存在或出现多个歧义候选时明确报错，不静默回退到系统默认设备。

### WakeWordDetector

- 使用官方 `sherpa-onnx-kws-zipformer-zh-en-3M-2025-12-20` 模型的 chunk-8 INT8 文件。
- 通过关键词文件同时配置 `露米` 和 `你好露米`，检测逻辑不能再限制为单一固定字符串。
- 只处理内存中的 16 kHz PCM，不联网、不保存休眠音频。
- 模型或运行库缺失时以可诊断错误停止，不进入高频重启循环。

### WakeReplyCache

- 以固定文本为键保存四个 WAV 文件，并记录合成参数版本，确保缓存可判定是否过期。
- 缓存缺失时只在显式准备步骤中调用豆包 TTS 生成；持续运行期间不隐式批量下载或覆盖文件。
- 播放时由注入的随机选择器选取回应；测试使用确定性选择器。

### StreamingAudio / Live ASR

- 复用现有 20 ms 音频块、200 ms 网络包、800 ms 尾静音和 10 秒上限。
- 增加短预滚缓冲，把语音起始阈值之前的少量 PCM 一并送入 ASR，解决当前真实测试中句首被裁切的问题。
- 云端连接只在本地判断用户开始说话后建立，不能上传休眠环境音。
- 豆包 ASR 使用 `wss://openspeech.bytedance.com/api/v3/sauc/bigmodel_async` 和资源 ID `volc.seedasr.sauc.duration`。

### ArkClient

- 使用 `https://ark.cn-beijing.volces.com/api/v3/chat/completions`、Bearer API Key 和已配置模型 `doubao-seed-2-0-lite-260428`。
- 保存本次 30 秒会话内的有限文本上下文；进入休眠时清空，避免上下文无限增长。
- 系统提示把角色限定为“露米”，回答使用简短、自然中文，第一版不输出或执行硬件动作。
- 设置回答长度上限和请求超时；日志只允许记录脱敏错误和供应商请求 ID。

### DoubaoTTS / AudioPlayer

- 使用当前豆包 TTS 2.0 单向流式 HTTP 接口：`https://openspeech.bytedance.com/api/v3/tts/unidirectional`。
- 请求头使用 `X-Api-Key`、`X-Api-Resource-Id: seed-tts-2.0` 和唯一 `X-Api-Request-Id`，不继续使用旧版 App ID / Access Token 鉴权头。
- 默认音色先保持文档示例 `zh_female_vv_uranus_bigtts`，音色更换属于后续配置调整，不影响编排接口。
- 音量由 ALSA 扬声器控制，正常 TTS 请求不使用云端额外增益。
- 播放命令必须使用参数数组且禁止 `shell=True`；只等待和终止当前进程创建的子进程。

### VoiceLoopOrchestrator

- 唯一负责状态机、30 秒截止时间、失败计数、300 ms 播放后保护时间和资源释放。
- 依赖通过接口注入：设备解析、KWS、录音/VAD、ASR、Ark、TTS、播放器、时钟和随机源。
- 任一阶段退出时关闭自己创建的录音、网络和播放资源；不得用全局进程清理命令。

## 配置与凭证

- 当前开发配置继续使用项目外或 Git 忽略的 `.env.voice`，文件权限保持 `0600`；不得提交或打印其中的密钥。
- ASR 与 TTS 的资源 ID 分开配置，避免把 `volc.seedasr.sauc.duration` 和 `seed-tts-2.0` 混用。
- 方舟使用 `ARK_API_KEY` 和 `ARK_MODEL_ID`；豆包 TTS 使用独立的 API Key 配置项。若当前同一 Key 有两个服务权限，也保持代码字段分离。
- 音频设备通过 USB 身份动态解析，不能永久写死 ALSA 数字卡号。
- KWS 模型放在项目约定的模型缓存目录，并通过配置指向；大模型文件不提交 Git。

## 错误处理

- 未检测到有效语音：不发送空请求，继续在当前 30 秒窗口监听。
- ASR 最终文本为空：作为一次可恢复失败，可播放简短的本地或云端提示；连续两次失败休眠。
- Ark、TTS 或网络失败：记录脱敏错误；一次失败后仍可监听，连续两次失败休眠。
- TTS 已生成但扬声器播放失败：立即停止会话并释放资源，避免重复播放。
- USB 设备中途拔出：停止相关子进程并返回可诊断错误，不切换到未知默认声卡。
- KWS 初始化失败：停止监听并返回非零退出码，不循环占用 CPU。
- 所有异常信息不得包含 API Key、Access Token、完整请求头或原始环境音频。

## 实施顺序

1. 更新纯配置和协议适配器，迁移 TTS 2.0 新接口并加入脱敏测试。
2. 扩展 KWS 配置以支持两个唤醒短语，增加模型完整性检查和关键词文件生成。
3. 安装轻量 `sherpa-onnx` 运行库并下载指定官方约 38 MB KWS 模型；下载后校验必需文件。
4. 实现唤醒回应缓存准备工具，并在用户确认后进行一次云端合成。
5. 为现有流式音频增加预滚缓冲，并保持当前阈值、尾静音和最长时长规则。
6. 实现半双工编排器和可执行 CLI。
7. 先运行单元与模拟集成测试，再分别进行云端 Ark、TTS、完整闭环和真实 USB 音频验证。

依赖安装、模型下载、云端调用和真实扬声器播放都应作为可见步骤执行；自动化单元测试不得访问网络、麦克风或扬声器。

## 测试与证据边界

### Static check

- 配置字段、资源 ID、端点、模型文件名、设备解析规则和密钥脱敏检查。
- 不能据此声称代码测试、云端调用或真实音频设备通过。

### Code test

- KWS 双短语配置与关键词文件测试。
- 四个精确回应及随机选择测试。
- 预滚、VAD、800 ms 尾静音、10 秒上限测试。
- 状态转换、300 ms 保护时间、30 秒会话超时和连续两次失败测试。
- ASR、Ark、TTS 请求/响应解析测试，全部使用模拟网络。
- 播放期间不会同时启动麦克风识别的并发约束测试。
- 日志及异常中不出现凭证测试。

### Cloud integration validation

- 分别执行一次 ASR、Ark 和 TTS 的最小真实请求，记录成功与供应商请求 ID，不记录密钥。
- 云端接口成功不等于 USB 播放或完整闭环成功。

### Physical audio-device validation

- 近距离分别说 `露米` 和 `你好露米`，验证本地唤醒。
- 验证四个缓存回应均可通过当前 USB 扬声器播放。
- 至少完成两轮无需重复唤醒的 ASR → Ark → TTS 对话。
- 验证播放期间不自收音，结束约 300 ms 后恢复监听。
- 验证 30 秒无有效语音后安静休眠。

以上只属于树莓派和 USB 音频设备验证，不得表述为固件上传、ESP32-S3 通信、舵机台架或装机验证。

## 第一版明确不做

- 播报中打断、全双工通话和声学回声消除。
- 情绪动作、灯光联动、GPIO、ESP32-S3 或舵机控制。
- 开机自启、系统服务和无人确认的自动更新。
- 保存休眠音频、长期保存对话录音或把原始音频写入日志。
- 自动安装大型 AI 框架；只使用 sherpa-onnx 及其指定小型 KWS 模型。

## 验收标准

- 断网时仍能在本地识别 `露米` 和 `你好露米`，且休眠音频不上传。
- 唤醒后随机播放四个精确回应之一，播放过程中不启动普通 ASR。
- 用户能在 30 秒窗口内完成至少两轮 ASR → Ark → TTS 对话，无需重复唤醒。
- 句首预滚避免已知的唤醒后问题开头裁切。
- 每次有效交流重置 30 秒计时，超时后安静休眠。
- 任何异常不会导致无限录音、无限播放或高频重试。
- 运行过程不访问 GPIO、串口、ESP32-S3 或舵机。

## 与 2026-08-26 设计的差异

- 唤醒短语由仅 `你好露米` 改为同时支持 `露米` 和 `你好露米`。
- 唤醒回应改为本轮确认的四句精确文本，并采用本地 WAV 缓存。
- TTS 从旧版 App ID / Access Token SSE 接口迁移到当前 API Key 单向流式 HTTP 接口。
- 加入播放后约 300 ms 保护时间、ASR 句首预滚和明确的 KWS 官方模型版本。
- 保留第一版半双工，打断功能推迟到后续独立设计。
