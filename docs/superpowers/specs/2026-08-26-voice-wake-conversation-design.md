# LumiLamp 本地唤醒与连续语音对话设计

日期：2026-08-26

## 目标

为 LumiLamp 增加本地离线唤醒和连续语音对话能力。休眠状态下只在 Raspberry Pi 本地检测唤醒词；唤醒后才把用户语音发送到豆包 ASR，并通过火山方舟大模型生成回答，再使用豆包 TTS 和 USB 扬声器播报。

第一版只实现语音交互，不设计或执行拟人动作。ESP32-S3 和舵机到货、安全确认及单关节验证前，不产生 GPIO、串口或电机输出。

## 已确认的产品行为

- 唤醒词：`你好露米`。
- 唤醒检测：使用 `sherpa-onnx`，在 Raspberry Pi 本地离线运行。
- 唤醒后进入连续对话状态；每次有效交流后重新开始 30 秒计时。
- 30 秒没有有效交流时安静休眠，不播放结束提示。
- 第一版不支持用户在 LumiLamp 播报过程中打断。
- 播报期间暂停普通语音识别，播报结束后恢复监听。
- 正式连续对话的扬声器音量目标约为 70%，避免最大音量造成回声和误识别。

## 唤醒反馈

唤醒成功后随机选择一句：

1. `嗯？`
2. `你好。`
3. `我在，怎么啦？`
4. `请吩咐。`

生产运行使用随机选择；自动化测试注入固定随机源，确保测试确定性。第一版只播放语音，不触发动作。

## 状态机

```text
SLEEPING
  │ 本地检测到“你好露米”
  ▼
WAKING
  │ 随机唤醒回应
  ▼
LISTENING
  │ 获取一段有效语音
  ▼
RECOGNIZING
  │ 豆包 ASR 返回文字
  ▼
THINKING
  │ 火山方舟返回文本回答
  ▼
SPEAKING
  │ 豆包 TTS 播放完成
  ▼
LISTENING
  │ 30 秒没有有效交流
  ▼
SLEEPING
```

任意不可恢复异常都应关闭当前录音/播放资源并返回 `SLEEPING`。

## 组件边界

### WakeWordDetector

- 只读取本地麦克风 PCM 数据。
- 使用 sherpa-onnx 中文关键词模型检测 `你好露米`。
- 不访问网络，不记录原始休眠音频。
- 只输出唤醒事件。

### ConversationController

- 唯一负责状态转换、30 秒超时和失败计数。
- 通过接口调用录音、ASR、LLM、TTS，不直接实现供应商协议。
- 接受可注入时钟和随机源，保证测试确定性。

### Recorder

- 复用现有 16 kHz、16-bit、单声道 USB 麦克风录音能力。
- 第一版单轮录音最长 10 秒；检测到用户开始说话后，连续静音 800 ms 即结束本轮录音。
- 静音阈值必须可配置，并在真实麦克风测试时校准；未检测到有效语音时不上传空白录音。

### Doubao ASR

- 复用已经验证的豆包 ASR 2.0 链路。
- 仅在 `LISTENING` 后上传用户主动说出的音频。
- 不在休眠监听期间上传环境声音。

### ArkClient

- 使用 `ARK_API_KEY` 和已配置的模型 ID。
- 输入为 ASR 文本，输出为简短中文回答。
- 第一版只允许文本回答，不生成或执行动作命令。
- 设置响应长度上限，避免 TTS 播放过长。

### Doubao TTS / Player

- 复用已经验证的豆包 TTS 2.0 和 USB 扬声器。
- 连续对话默认将 USB 扬声器设置为约 70%。
- `SPEAKING` 状态期间暂停普通 ASR，防止系统听到自己的声音。

### ActionSink

- 第一版只提供无副作用的模拟接口并记录事件。
- 不包含 GPIO、串口、ESP32-S3 或舵机实现。
- 后期动作设计应通过独立设计和真实硬件安全确认接入。

## 数据与凭证

- 私密配置继续保存在 `/home/lamp/.config/lumilamp/voice.env`，权限保持 `0600`。
- 日志不得记录 Access Token、Secret Key 或 Ark API Key。
- 临时对话录音保存在 `/tmp`；当前项目规则禁止自动删除文件，因此第一版应明确记录临时文件路径，并在获得删除授权前保留。
- 休眠唤醒音频不写入磁盘。

## 异常策略

- 没有识别到有效文字：播放 `我没听清，可以再说一次吗？`，保持对话状态。
- 网络、ASR 或 LLM 暂时失败：播放 `网络好像开小差了。`。
- 连续两次处理失败：停止当前会话并安静返回休眠。
- TTS 或扬声器播放失败：记录脱敏错误并直接返回休眠，不循环重试播放。
- 唤醒引擎失败：记录脱敏错误，停止持续监听，避免高 CPU 重启循环。

## 测试策略

### 静态和单元测试

- 状态转换与 30 秒超时使用虚拟时钟测试。
- 四个唤醒回应使用固定随机源测试。
- 连续两次失败返回休眠。
- `SPEAKING` 状态不会同时启动 ASR。
- ActionSink 只产生模拟事件，没有硬件 I/O。
- 日志和对象表示不包含任何密钥。

### 软件集成测试

- 使用录制样本验证本地关键词检测，不访问云端。
- 使用现有 MockBus 确认语音流程不产生动作指令。
- 分别验证 ASR、Ark、TTS，再验证完整半双工闭环。

### 真实音频设备验证

1. 近距离唤醒词检测。
2. 一米距离唤醒词检测。
3. 安静环境误唤醒观察。
4. 扬声器 70% 播报时确认麦克风不会进入普通 ASR。
5. 30 秒超时后确认恢复本地监听。

这些属于 USB 麦克风与扬声器验证，不得表述为 ESP32-S3 或舵机验证。

## 第一版明确不做

- 全双工通话和播报中打断。
- 声学回声消除。
- 情绪动作与舵机控制。
- ESP32-S3 通信。
- 摄像头、人物跟踪或灯光联动。
- 系统启动服务和开机自启。
- 云端持续监听。

## 验收标准

- 断网时仍能本地检测 `你好露米`，但不会错误进入云端对话。
- 唤醒后随机播放四个确认回应之一并进入连续对话。
- 用户可以在 30 秒窗口内完成至少两轮 ASR → Ark → TTS 对话，无需重复唤醒。
- 每次有效交流重置 30 秒计时，超时后安静休眠。
- 播报期间不启动普通 ASR。
- 任意异常不会造成无限录音、无限播放或高频重试。
- 整个流程不访问 GPIO、串口、ESP32-S3 或舵机。
